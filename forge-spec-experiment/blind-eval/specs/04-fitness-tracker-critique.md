# 产品需求规格说明书 (Product Spec) - 健身追踪 App “IronLog”

## 1. 产品概述

**产品名称：** IronLog (代号)

**产品定位：** 一款面向**核心健身爱好者**（主要是20-35岁男性，有1年以上训练经验）的个人训练记录与分析工具，兼顾轻量社交与成就激励。它不是一个“新手健身教学App”，而是一个“老手的训练日志与分析平台”。

**核心价值主张：** 比 Excel 更专业，比 Keep 更纯粹。专注于**数据记录、趋势分析和计划管理**。

## 2. 目标用户

*   **核心用户：** 20-35岁，有1年以上系统训练经验的男性健身爱好者。他们熟悉健身术语（RM, RPE, 超级组等），对训练数据敏感，有自我驱动的进步需求。
*   **次要用户：** 有1年以上训练经验的女性健身爱好者；希望从纸质/Excel记录转向数字化记录的资深训练者。

## 3. 核心功能 (含风险标注和替代方案)

### 3.1 训练记录模块

*   **功能描述：** 用户创建训练，添加动作，记录每组数据的重量、次数和休息时间。支持RPE/RIR记录。支持编辑、删除、复制历史训练。
*   **隐含假设：** 用户知道如何正确完成动作，且能熟练操作手机。
*   **模糊点：**
    *   “组数”的定义：是正式组还是包括热身组？（**明确化：** 允许用户添加“热身组”标签，或者默认只记录正式组，但提供“添加热身组”选项。）
    *   “记录每组数据”的操作流程：是滑动滑块还是手动输入数字？（**明确化：** 采用数值键盘输入，同时提供“+2.5kg”、“+1rep”的快捷按钮，模拟真实增重/增次习惯。）
*   **风险标注：**
    *   **风险：** 训练中操作手机繁琐，打断训练节奏。
    *   **替代方案：** 提供**“免打扰模式”**：锁屏状态下，通过Apple Watch/小米手环或手机侧键快速记录（例如：双击侧键记录“+1组，重量不变”）。核心逻辑是**最小化操作步骤**。
*   **范围裁剪建议：** **V1核心功能**，必须实现。

### 3.2 进步曲线与分析

*   **功能描述：** 针对每个动作（如卧推），以时间为X轴，以“1RM估算值”、“最大重量”、“总容量”等为Y轴，生成折线图。
*   **隐含假设：** 用户会持续、规律地进行相同动作，数据才有分析价值。
*   **模糊点：** “进步”的定义？是最大重量提升，还是总容量（重量x组数x次数）提升？（**明确化：** 默认显示“1RM估算值”趋势，同时提供“总容量”和“最大重量”视图切换。提供“预估1RM”算法（如Epley公式）的说明。）
*   **风险标注：**
    *   **风险：** 数据稀疏（用户只练了一次卧推）导致曲线无意义。
    *   **替代方案：** 仅当某个动作被记录超过3次且时间跨度超过2周后，才激活其曲线分析功能。前期只显示“数据不足”提示。
*   **范围裁剪建议：** **V1核心功能**，必须实现。

### 3.3 动作库管理

*   **功能描述：** 内置200+常见动作（含标准名称、目标肌群、动作示意图/GIF）。支持用户自定义动作（名称、肌群、类型）。
*   **隐含假设：** 用户能准确判断动作的目标肌群。
*   **模糊点：** “常见动作库”的标准是什么？（**明确化：** 基于《力量训练解剖学》和主流健身App（如Strong, Hevy）的数据库，按部位（胸、背、腿、肩、手臂、核心）分类。每个动作必须关联1个主要肌群+1个次要肌群。）
*   **风险标注：** 无重大风险，但自定义动作的审核和搜索需要设计好。
*   **范围裁剪建议：** **V1核心功能**。内置动作库可分批上线。

### 3.4 训练计划设计与管理

*   **功能描述：** 用户创建、编辑、删除训练计划（如：推-拉-腿分化）。计划包含：动作列表、目标组数、目标次数范围、目标重量/RPE。支持计划分享（生成链接或二维码）。
*   **隐含假设：** 用户了解训练计划的结构（如分化、渐进超负荷）。
*   **模糊点：** “分享给别人”的格式是什么？（**明确化：** 分享为“只读快照”，接收方可以“复制”该计划到自己的账户下进行修改。不提供“共同编辑”功能。）
*   **风险标注：**
    *   **风险：** 计划分享可能导致版权或内容质量问题（例如分享错误/有害的计划）。
    *   **替代方案：** 分享时增加“免责声明”，并允许用户举报不当计划。不设官方推荐，完全UGC。
*   **范围裁剪建议：** **V2功能**。V1阶段只提供“保存历史训练为模板”的简化功能。

### 3.5 社交与动态

*   **功能描述：** 添加好友（通过手机号/用户名），查看好友的公开训练动态（如“张三完成了‘推类训练’，卧推5x5 @ 80kg”）。支持点赞和评论。
*   **隐含假设：** 用户愿意公开自己的训练数据。
*   **模糊点：** “看到朋友的训练”的颗粒度？（**明确化：** 默认仅公开“训练名称、完成状态和核心动作的最高成绩”。具体组数、重量、RPE等详细数据默认隐藏。用户可在设置中调整隐私级别：公开/好友可见/仅自己。）
*   **风险标注：** **高合规风险**。涉及用户数据隐私（训练数据属于个人健康信息）。需要符合《个人信息保护法》要求。
*   **替代方案：** **V3或不做**。鉴于隐私风险和开发成本，建议在V1/V2阶段**砍掉社交功能**。可以先用“排行榜”或“成就系统”替代社交互动。
*   **范围裁剪建议：** **V3或不做**。强烈建议V1/V2不包含。

### 3.6 打卡与成就系统

*   **功能描述：** 每次完成训练后自动打卡。连续打卡天数形成“连胜记录”。解锁成就徽章（如“铁人周”、“100次训练”等）。
*   **隐含假设：** 用户有持续训练的动力，且打卡能激励他们。
*   **模糊点：** “连续打卡”的定义？如果一天训练两次，算一次还是两次？（**明确化：** 一个自然日内，完成至少一次训练即算打卡成功。不重复累计。）
*   **风险标注：** 无重大风险，但成就设计需有吸引力，避免沦为“为了打卡而打卡”的空洞设计。
*   **范围裁剪建议：** **V1核心功能**。成就系统可设计为动态更新的“任务”，而非一次性徽章。

### 3.7 智能穿戴设备接入

*   **功能描述：** 连接Apple Watch（iOS端）和小米手环（Android端），实现：1) 自动开始/结束训练（基于心率）；2) 在手表上快速记录组数；3) 同步训练消耗的卡路里和心率数据到训练总结。
*   **隐含假设：** 用户拥有并佩戴这些设备，且愿意授权数据。
*   **不可行性分析：**
    *   **小米手环：** 小米手环的API开放程度极低，通常只能获取步数、睡眠等基础数据。**无法实现“在手表上快速记录组数”**。其“训练模式”API也受限于小米运动App，第三方App很难深度控制。
    *   **Apple Watch：** 可行。WatchKit支持自定义表盘复杂功能、Workout API和HealthKit数据读取。
*   **替代方案：**
    *   **Apple Watch：** V2可实现。
    *   **小米手环：** **V2阶段放弃深度集成**。改为仅同步小米运动App中的“训练开始/结束事件”和“总卡路里”数据。**记录组数功能无法实现**，可引导用户使用手机操作。或者，**考虑支持更开放的手表平台，如Wear OS或Amazfit的Zepp OS**。
*   **范围裁剪建议：** **V2或不做**。仅支持Apple Watch深度集成。小米手环仅做基础数据同步（V3）。或者，**V1阶段完全不接入任何穿戴设备**，优先打磨核心记录体验。

## 6. 前提条件

*   **技术前提：**
    *   开发团队具备iOS (Swift/SwiftUI) 和 Android (Kotlin/Jetpack Compose) 原生开发能力。
    *   后端服务 (Go/Node.js + PostgreSQL) 稳定可靠，支持高并发数据存储和分析。
    *   与Apple HealthKit、WatchKit API的对接完成。
*   **业务前提：**
    *   获得用户对训练数据收集和使用的明确同意（隐私协议）。
    *   内置动作库的版权和内容准确性问题已解决（购买数据库或自行整理）。
*   **资源前提：**
    *   配备1名UI设计师（擅长数据可视化）、1名后台开发、2名客户端开发。
    *   预留至少3个月的开发周期。

## 7. 用户流程 (核心场景)

**场景：用户完成一次“推类训练”**

1.  **打开App** -> 首页显示今日计划（如果有）或“开始新训练”按钮。
2.  **选择/创建训练** -> 点击“推类训练”计划（V1为模板，V2为自定义计划）。
3.  **开始训练** -> App进入“训练模式”，屏幕常亮，显示当前动作列表。
4.  **记录第一组（杠铃卧推）**：
    *   点击“杠铃卧推” -> 输入重量“80kg” -> 输入次数“5” -> 点击“完成组”。
    *   自动开始60秒休息倒计时。
5.  **休息后** -> 倒计时结束，自动回到“杠铃卧推”页面，准备记录下一组。
6.  **完成所有动作** -> 点击“结束训练”。
7.  **训练总结** -> 显示总时长、总容量、每组数据摘要、预估1RM变化（与上次对比）。
8.  **自动打卡** -> 成就系统更新，连续打卡天数+1。

## 8. 技术要求

*   **前端：** 原生开发（Swift / Kotlin），确保流畅的动画和列表性能。
*   **后端：** 基于RESTful API，使用WebSocket实现实时数据同步（如手表记录）。
*   **数据库：** 关系型数据库（PostgreSQL）存储用户、训练、动作数据。时序数据库（如TimescaleDB）存储进步曲线数据，以优化查询性能。
*   **数据安全：**
    *   HTTPS传输。
    *   用户ID与训练数据加密存储。
    *   所有社交相关功能（V3）需有严格的数据访问控制。
*   **离线支持：** 训练记录必须在无网络环境下可用，数据在联网后自动同步。
*   **性能指标：** 训练记录页面加载时间 < 200ms；进步曲线图表渲染时间 < 1s。
