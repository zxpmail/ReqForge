### 1. 产品概述

**产品名称:** 知源 (暂定)
**产品定位:** 面向公司全体员工的、统一、高效、智能的企业内部知识管理与协作平台。
**核心目标:** 解决当前信息分散（微信群、共享文件夹）、检索困难、知识沉淀不足的问题，提升信息查找效率与组织知识复用能力。
**价值主张:** 让每位员工都能在3秒内找到所需信息。

---

### 2. 目标用户

| 用户类型 | 用户画像 | 核心需求 | 技术能力 |
| :--- | :--- | :--- | :--- |
| **全体员工 (170人)** | 非技术背景为主，日常使用办公软件。 | 快速找到公司制度、流程、项目文档等。操作简单，无需学习成本。 | 低 |
| **技术团队 (30人)** | 开发、运维、测试等。 | 技术方案、API文档、代码规范、架构图等。支持Markdown，追求效率。 | 高 |
| **管理员/HR** | 负责内容管理、权限控制、新员工入职。 | 批量导入文档、设置分类、管理用户权限。 | 中 |

### 3. 核心功能 (含风险标注和替代方案)

#### 3.1 文档分类与组织

*   **功能描述:** 支持按“部门”（如：技术部、市场部）和“项目”（如：A项目、B项目）创建多级分类目录。支持标签（Tag）系统，一篇文章可打多个标签。
*   **风险标注:**
    *   **风险1 (模糊描述):** “按部门、项目分类”过于笼统。部门可能交叉（如跨部门项目），项目可能变更。**建议明确化：** 采用“项目空间”+“标签”的混合模式。每个项目/部门有一个独立空间，空间内可建文件夹。标签作为跨空间的补充。
    *   **风险2 (隐含假设):** 假设所有人都愿意主动分类。**替代方案:** 提供“待分类”回收站，管理员可定期整理。或引入AI自动分类（v2功能）。
*   **范围裁剪建议:** **V1实现。** 先支持两级分类（空间->文件夹），标签系统作为V2。

#### 3.2 全文搜索

*   **功能描述:** 支持对文档标题、正文内容（包括Word和Markdown）进行快速搜索。支持模糊匹配、关键词高亮。
*   **风险标注:**
    *   **风险 (不可行部分):** “要快”是主观感受。200人、假设10万份文档，使用Elasticsearch可以做到毫秒级响应，可行。但Word文档需要后台解析全文，首次解析有延迟。
    *   **替代方案:** 使用成熟的搜索引擎中间件（如Elasticsearch、Meilisearch）。
*   **范围裁剪建议:** **V1核心功能，必须实现。**

#### 3.3 文档上传与预览

*   **功能描述:**
    *   支持上传 `.md` 和 `.docx` 文件。
    *   支持在网页端直接预览渲染后的Markdown和Word文档。
    *   Word文档上传后自动转换为网页可读格式（如HTML）。
*   **风险标注:**
    *   **风险 (隐含假设):** 用户上传的Word文档格式可能复杂（表格、图片、嵌入对象）。**明确化：** 需要明确支持的Word版本（.docx优先，.doc可能不支持）和格式限制（如不支持宏）。
    *   **替代方案:** 使用成熟的文档转换引擎（如LibreOffice或云服务API）。
*   **范围裁剪建议:** **V1实现。** 仅支持 `.md` 和 `.docx`，`.doc` 暂不支持。

#### 3.4 新人权限自动分配

*   **功能描述:** 当HR在HR系统中录入新员工信息后，系统自动创建账号，并根据其部门、角色（如“技术部-开发”）自动分配对应知识库空间的“查看”或“编辑”权限。
*   **风险标注:**
    *   **风险1 (不可行部分):** 前提是必须有HR系统并开放API接口。如果公司没有统一HR系统，此功能无法实现。**替代方案：** 管理员在后台手动创建用户并分配权限（V1实现）。或者通过企业微信/钉钉等第三方身份源同步。
    *   **风险2 (模糊描述):** “自动分配知识库权限”需要明确权限粒度（只读、读写、管理）。**建议明确化：** 定义三种角色：访客（只读）、贡献者（读写）、管理员。
*   **范围裁剪建议:** **V2实现。** V1先做手动添加用户和角色分配。V2对接HR系统或SSO（单点登录）。

#### 3.5 AI 文档总结 (v1.5 或 v2)

*   **功能描述:** 用户打开一篇长文档时，点击“AI总结”按钮，系统自动生成摘要（100-300字），并提取3-5个关键点。
*   **风险标注:**
    *   **风险 (不可行部分):** 依赖大语言模型（LLM）API，会带来**成本**（按token付费）和**数据安全**风险（文档内容可能外泄给第三方AI服务商）。
    *   **替代方案:**
        1.  **V1不做。** 这是一个锦上添花的功能，不是核心痛点。
        2.  **V1.5 做本地化模型：** 使用开源模型（如Llama 2）在公司内网服务器上部署，成本高但数据安全。或使用国产大模型（如百度文心、阿里通义千问）的私有化部署方案。
        3.  **功能简化：** 只对标题、标签、首段进行关键词提取，而非全文总结。
*   **范围裁剪建议:** **V2 或 V3。** 列为“探索性功能”，不承诺上线时间。

#### 3.6 用户体验 (UI/UX)

*   **功能描述:** 界面简洁、美观，交互流畅。支持深色模式。移动端适配良好。
*   **风险标注:**
    *   **风险 (模糊描述):** “好看一点”是主观的。**建议明确化：** 提供2-3套UI风格供选择（如：清爽白/商务蓝），并确保符合公司VI规范。
    *   **替代方案:** 采用主流设计系统（如Ant Design、Element Plus），保证基础美观度和一致性。
*   **范围裁剪建议:** **V1核心。** 保证基础美观、易用、响应式。深色模式、动效等作为V2优化项。

### 6. 前提条件

1.  **基础设施：** 公司需要提供一台服务器（或云服务器）用于部署服务。预计配置：4核8G，100GB SSD。
2.  **数据准备：** 需要成立一个兼职的内容管理小组（2-3人），负责V1上线前将现有共享文件夹中的核心文档进行清洗、分类、上传。
3.  **管理支持：** 需要公司高层或行政部发文，明确知识库为**唯一官方文档存储平台**，并推动全员使用。
4.  **IT协作：** 如果V2要实现自动权限，需要IT部门开放HR系统或SSO接口。

---

### 7. 用户流程 (以“查找公司制度”为例)

1.  **用户：** 新员工小明需要查找《员工考勤制度》。
2.  **操作：** 打开公司内网或浏览器，进入“知源”首页。
3.  **搜索：** 在搜索框输入“考勤制度”或“考勤”。
4.  **结果：** 系统展示匹配的文档列表，标题和内容中“考勤”关键词高亮显示。
5.  **浏览：** 小明点击结果，页面直接渲染出Word文档内容（无需下载），或者显示Markdown格式。
6.  **操作：** 小明可以收藏该文档，或点赞。
7.  **反馈：** 如果没找到，小明可以点击“未找到？提交需求”按钮，通知管理员。

### 8. 技术要求

*   **后端语言:** Go 或 Java (推荐Go，性能好，部署简单)
*   **数据库:** PostgreSQL (文档元数据、用户、权限) + Elasticsearch (全文搜索)
*   **对象存储:** MinIO (或阿里云OSS/腾讯云COS) 用于存储原始文档文件
*   **前端框架:** React 或 Vue 3 + Ant Design
*   **文档转换:** LibreOffice 或 Pandoc (用于Word转HTML)
*   **部署方式:** Docker容器化，支持Kubernetes (可选)
*   **API风格:** RESTful API
