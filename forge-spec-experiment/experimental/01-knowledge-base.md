# Product Spec: 企业内部知识库

## 产品概述
将散落在微信群和共享文件夹的知识集中管理。但需明确：这不是一个"工具问题"，而是"习惯问题" — 即使系统建好，如果员工不主动上传和维护，知识库依然是空的。

## 目标用户
- 全体员工 200 人（技术 30 人）
- **假设验证**: 非技术员工（170 人）中，有多少人愿意主动贡献内容？如果只是"消费"，知识库内容从哪里来？

## 核心功能

### 1. 文档管理
- 分类体系（部门+项目）
- **风险**: 客户要求"按部门/项目分类"，但未说明内容归属关系（一篇文档可以属于一个部门、三个项目吗？）。若无明确规则，分类会很快混乱
- **建议**: 定义文档归属规则：一篇文档有且仅有一个"所属部门"，可关联多个"标签"

### 2. 全文搜索
- 标题+内容搜索
- **隐含假设**: "搜索要快" — 未指定文档量级。如果是 200 人几年积累，文档可能在 5000-20000 篇，Elasticsearch 可以处理，但需要部署和维护。若规模远小于此，数据库 LIKE 搜索加索引就够
- **不可行的部分**: "3 秒内返回结果" — 对全文搜索来说这是底线，不是目标。应该定义为 <500ms

### 3. 文档上传
- Markdown + Word
- **未说明**: 版本管理 — 文档更新后旧版本是否需要保留？Word 文档的格式保留到什么程度？
- **建议**: v1 只支持 Markdown（轻量 + 版本可控），Word 上传仅做预览/转为 Markdown

### 4. 权限管理
- 按角色/部门自动分配
- **不可行**: "新人入职自动分配" 需要与 HR 系统对接或手动标记部门信息。没有 HR 系统对接，这个"自动"不可能实现
- **替代方案**: 手动选择部门+角色触发权限模板

### 5. AI 文档总结
- **风险**: 放在 v2 合理。当前阶段内容积累才是首要问题 — 没有内容，AI 没什么可总结的

### 6. 用户体验
- **模糊需求**: "好看一点，用户体验好" 不可度量。建议明确定义：阅读体验（字体/排版/暗黑模式）还是操作体验（减少点击次数）

## 范围裁剪建议
- **v1（核心）**: Markdown 文档 CRUD + 分类标签 + 基础全文搜索 + 手动权限分配
- **v2**: Word 上传 + 版本管理 + AI 总结
- **建议砍掉**: AI 总结在 v1 阶段没有内容支撑，做了也是摆设

## 风险矩阵
| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 员工不用 | 高 | 项目失败 | 必须有内容 cold start 策略，如强制迁移旧文档 |
| 内容过期 | 中 | 知识库变成垃圾堆 | 文档过期标记+定期 review 提醒 |
| 权限越复杂越没人用 | 中 | 用户体验下降 | 默认全员可见，敏感文档单独控制 |

## 前提条件
1. HR 系统或组织架构数据可用（否则"自动分配权限"不成立）
2. 管理层支持强制迁移旧文档（否则内容冷启动失败）
3. 定义文档分类规则和维护责任人
