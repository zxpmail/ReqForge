# 长对话记忆系统：三个方案，一张成本表

> 2026 年主流模型都支持 128K+ 上下文了，但"能用"和"用好"之间，隔着一层预算管理。

---

前段时间在做一个长对话记忆系统。8K Token 的上下文窗口里要装下 100 轮对话——数学上就不可能，除非你愿意接受失忆。设计时遇到了三组取舍。把它们写下来，不是给你标准答案的，是帮你少走弯路的。

---

## 方案一：及格线——推翻 8K 前提，拥抱长窗口

既然主流模型（GPT-4o、DeepSeek-V3、Claude 3.5）已支持 128K~1M 上下文，最简单的做法是：放弃摘要+向量检索的拼凑方案，全量塞入最近 50 轮原文。

**怎么操作**：
- 将最近 50 轮原文（约 3 万 Token）直接放入 System Prompt 下方

**怎么解决"中间遗忘"**：
- System Prompt 放在 Prompt 开头（前 1K Token）
- 用户当前问题放在 Prompt 结尾（后 1K Token）
- 论文证实模型对开头和结尾的记忆最好

**怎么兜底**：
- 对话超过 200 轮、总量超过 128K 时：滑动窗口保留最近 100 轮 + 前置全局摘要

**成本代价**：
- 单次对话 Token 消耗大幅上升（见下表）
- 但工程复杂度极低，不需要向量库、不需要检索服务

**隐藏成本**：TTFT（首 Token 时间）。3 万 Token 的 Prefill 时间大约是 3K Token 的 10 倍。高并发下 GPU 算力容易被 Prefill 占满，吞吐量腰斩。如果 QPS 超过 10，方案一的 GPU 成本可能比方案二贵 3-5 倍。

*花最多的算力，偷最大的懒。*

---

## 方案二：优秀线——弹性预算管理器

如果业务要抠成本，8K 窗口加动态分配比固定分配可靠得多。

### 动态降级（解决 System Prompt 膨胀）

```
可用上下文 = 8192 - SystemPrompt实际长度 - 输出预留(1500)
if 可用上下文 < 3000:
    触发降级：放弃滚动摘要，放弃向量检索
    只保留最近 3 轮原文 + 用户画像标签
```

### 双通道召回 + 重排序（解决延迟和中间遗忘）

- 向量库（语义）和 BM25（关键词）并行查询，各自 Top 5
- Cross-Encoder 重排序后取 Top 3（约 1500 Token）
- 强制插入 System Prompt 之后、工作记忆之前

### 异步缓存与预热（解决检索延迟）

- 用户第一句话进入时，后端异步生成滚动摘要，不阻塞当前回答
- 第二句话时摘要已就绪，直接读缓存。用户体感延迟只发生在第一轮

### 兜底熔断

- 摘要生成超时/失败 → 直接丢掉最旧的一半轮次，系统永远可用

*不是最优解，但最不会让你后悔。*

---

## 方案三：进阶线——自适应路由

如果要做平台级系统，不预设参数，让系统自己学会怎么分配。

```
每次请求进入时执行：
1. 实时计算 System Prompt + 当前问题的精确长度
2. 轻量级路由模型判断用户意图：
   - "闲聊" → 80% 剩余预算给最近工作记忆
   - "查历史细节" → 60% 预算给向量检索结果
3. 输出前验证三个指标：
   - 关键信息召回率 > 95%（需标注集测量）
   - P99 首 Token 延迟 < 800ms
   - Token 浪费率 < 10%
```

这套系统不需要人工调参，每天根据线上日志自动调整权重。

**注意**：三个指标中的"关键信息召回率"需要标注集支持——没有 ground truth 就无法测量。建议上线初期用方案二，积累足够日志后再迁移到方案三。

*自适应不是写在代码里的，是从日志里长出来的。*

---

## 三个方案怎么选

| 维度 | 方案一（128K 全量） | 方案二（弹性预算） | 方案三（自适应路由） |
|------|-------------------|------------------|-------------------|
| 单次对话平均 Token 消耗 | ~3 万 Token | ~2K-6K Token | ~4K-8K Token |
| 工程复杂度 | 低 | 中 | 高 |
| 检索延迟 | 无 | <200ms | <800ms |
| 兜底机制 | 滑动窗口 | 摘要失败降级为滑动窗口 | 路由失败退化为方案二 |
| 团队能力要求 | 初级工程师即可 | 需要懂检索和降级策略 | 需要算法工程师 + 标注团队 |
| 上线周期 | 1 周 | 3-4 周 | 2-3 个月（含标注和调优） |
| 故障排查难度 | 低（只有模型报错） | 中（需排查检索、摘要、缓存三路） | 高（路由决策错误难以定位） |
| 适用场景 | 创业公司 MVP 快速验证 | 大多数 ToC 产品的最佳起点 | 日活百万级、算力成本为主要矛盾 |

**建议**：大部分团队止步于方案一或二就够了。方案三需要标注集和线上日志——不是每个项目都配得起这套基础设施。

---

## 最后

三方案不是递进的——方案二在大多数场景下是"正确"的选择，方案一在资源充足的场景下是"够用"的选择，方案三在数据丰富的场景下是"更好"的选择。看清自己的约束条件再来选，而不是选最复杂的那个。

**实施路线图**：先用方案二上线。等日志积累到一定规模后，通过 A/B 测试对比方案二和方案三的表现。确认方案三在召回率和延迟上确实有显著提升再迁移——不要为了"更先进"而换方案。

*写于 2026-06。三个方案，一张成本表，七条兜底机制。*
