# 你的 Agent-Native 只做了前三层

> 真正的第四层，是让 Agent 知道自己做得对不对。

---

你可能已经听说过「Agent-Native」这个词了。

BuilderIO 开源了同名框架，阿里云在峰会上展示了五款 Agent-Native 产品，社区里开始讨论「Agent-Native 设计范式」。

但如果你去翻这些讨论，会发现一个奇怪的现象：大部分解释都把 Agent-Native 等同于「让 AI 操作 UI」——Agent 感知 DOM 树、Agent 点按钮、Agent 和前端深度绑定。

这个理解，对，但极其片面。

它看到了前三层，漏掉了最关键的一层。

---

## 一、大家都在说的三层

当前讨论中有一个反复出现的三层模型：

**第一层：内容可读**

Agent 能把你的内容理解为结构化文本，而不是被 JavaScript 渲染的噪音。llms.txt、AGENTS.md 这类标准解决的就是这个问题。

**第二层：任务可执行**

Agent 不只是读——它能调用你的 API、触发操作、获取实时数据。defineAction 及其等价物解决的就是这个问题。

**第三层：协议兼容**

Agent 通过标准协议（MCP、A2A）与系统交互，你不用为每个 Agent 写定制适配。一套协议，所有 Agent 都能用。

这三层回答了同一个问题：「Agent 怎么操作这个产品？」

这个问题很好。但它不是唯一的问题。

把 Agent-Native 仅仅定义在这三层上，就错过了更难的那一半。

---

## 二、「原生」不是原生于 React

说回那个定义。

BuilderIO 官方写的是：「让人类和 AI Agent 通过共享的操作、数据、权限和上下文来操作同一个产品。」

核心精神是对的——共享的、原生的、多面的。

但社区把「原生」理解成了「原生绑定到前端框架」——具体说就是 React。这是一个危险的窄化。

一个真正的 Agent-Native 系统，应该让 Agent 通过稳定的协议来交互——CLI、HTTP API、MCP、A2A——而不是硬编码到一棵 DOM 树上。

为什么？因为稳定性完全不同：

UI 框架（React、Vue 等）的生命周期是 2-5 年。换一个框架就得重来。

CLI 命令与参数约定的生命周期是 20-50 年。缓慢演进，向后兼容。

协议（HTTP、SQL、MCP）的生命周期是 30-50 年。从不替换，只会扩展。

UI 是易变的——今天 React，明天 Vue，后天直接语音交互。把 Agent 的逻辑绑死在 DOM 上，前端一重构，Agent 直接失明。

协议是持久的。Agent 应该 Native 在这些稳定的基石上，而不是易变的表现层。

三层模型在精神上是正确的。但它的实现必须是协议优先的，不是 UI 优先的。

---

## 三、这三层具体是什么

来认真定义一下。因为第四层的重量，只有在你充分感受了第三层的成就——以及它的局限——之后才能真正理解。

**第一层：内容可读**

Agent 能从你的内容中提取结构化的含义。不是渲染后的 HTML，不是 JavaScript 拼出来的噪音——而是干净、可解析的文本。

你自测：一个模型打开你的文档，能不能在不滚动无关内容的情况下找到它需要的接口？

**第二层：任务可执行**

Agent 能对系统采取行动。它能创建记录、触发工作流、查询数据。

关键的架构决策是：把操作定义一次，然后同时暴露给 UI 和 Agent——走同一个接口。

你自测：Agent 能不能在你的产品里做到人类用户通过 UI 能做的一切——而且完全不碰 UI？

**第三层：协议兼容**

Agent 通过开放标准操作，而不是定制的胶水代码。它对你的服务讲 MCP，对其他 Agent 讲 A2A。

你自测：你的系统能不能兼容任何 MCP 兼容的 Agent——还是只能配你自己写的那一个？

这三层给你一个具有操作能力的 Agent。它能读、能做、能互操作。

很多团队做到这里就觉得满了。说得过去——大部分产品连第一层都没做好。

但第三层上面有一个无人讨论的空隙。

---

## 四、第四层：元认知

前三层让 Agent 有能力。但能力没有自知之明是危险的。

第四层回答的是另一个问题——不是「Agent 怎么操作产品？」，而是「Agent 怎么知道自己操作对了——做错了又怎么办？」

这就是元认知层。它有三个子能力：

**能力意识**

Agent 知道什么事自己能做、什么事自己做不准。

「这段代码我可以生成，但安全模型应该让人来审。」

「这个错误模式我之前犯过——先查一下参考文档再动手。」

「这个问题不在我的能力范围内——转给专家系统。」

没有这个，一个拥有前三层的 Agent 会自信地尝试所有它能触及的事。一个强大的工具，却没有边界感。

**自我进化**

Agent 注意到自己的失败模式，并自我修正。

「同样的 PostgreSQL 迁移错误我已经犯了三次了。我应该写一份参考文档，以后生成迁移之前先查一下。」

「这个错误模式在反馈里反复出现——我应该提出一个新的规则来预防。」

「反馈条目积累了 12 条——是时候触发一次进化周期，审视自己的启发式规则了。」

这是「等着人来修的工具」和「维护自己能力的操作者」之间的区别。

**优雅降级**

Agent 能说清楚自己为什么做不了。

「我不能改这个文件——它不在当前阶段的范围内。」

「我不能回答这个问题——它不是我当前配置的领域。」

「我发现了规格和代码之间的矛盾。我会把它标记出来，而不是默默选一个。」

用产品语言说：前三层让 Agent 成为你产品的高级用户。第四层把它变成了一个负责任的运营者——在问题出现时会主动「拉闸」。

一个成熟度模型来收一下：

📖 第一层：内容可读 → Agent 可以阅读
🛠️ 第二层：任务可执行 → Agent 可以动手
🤝 第三层：协议兼容 → Agent 可以互操作
🧠 第四层：元认知 → Agent 认识自己

## 五、两种架构，同一个理念

两个挂着 Agent-Native 标签的框架，用完全不同的架构回答了同一组问题。

**BuilderIO agent-native** — SaaS 产品路线
- 主要界面：React UI + Agent
- 共享状态：数据库（Drizzle）
- 操作方式：defineAction
- 元认知策略：审计日志 + 权限控制

**ReqForge** — 工程工具路线
- 主要界面：CLI + 文件系统
- 共享状态：文件系统（git）
- 操作方式：Skill 命令 + Hook
- 元认知策略：反馈循环 + 钩子

BuilderIO 把元认知当成**审计问题**——记录谁干了什么，用 RBAC 划边界。对 SaaS 产品这是合理起点：人类仍是主要操作者，Agent 是助手。

ReqForge（说明：我构建的框架）把元认知当成**操作系统问题**——在执行路径上插入钩子，强制正确性、积累反馈、触发自我改进。

差异不是谁更好——而是**领域塑造的**。SaaS 产品需要权限边界。工程工具需要正确性反馈循环。第四层在不同领域呈现不同形态。

关键是它存在。

---

## 六、走向第四层的三个具体决策

如果你今天在设计一个 Agent-Native 系统，希望朝第四层迈进，有三个现在就可以做的决策。

**决策一：让状态透明**

当 Agent 和人类共享一个状态层时，Agent 的历史也是它的自我模型。

如果共享状态是数据库，你需要不可篡改的审计日志来追踪谁做了什么。如果共享状态是文件系统，git log 就是审计线索——Agent 读自己的历史，从自己的错误中学习。

在 SaaS 场景中，透明意味着让每一个 Agent 的行为通过 Agent 自己使用的接口也能被观察到——而不是藏在某个独立管理后台里。

透明才能自我修正。看不到自己做了什么的人，改不了。

**决策二：在环境层面强制约束，不是在提示词层面**

把元认知检查写在系统提示词里是脆弱的。换一个模型版本、换一种提示词结构，Agent 就忘记自我检查了。

稳健的做法是钩子——在特定的执行点运行的拦截器，不管模型怎么决定都会触发。

例如：写代码之前检查规格是否确认、生成之后检查引用是否真实、声称完成时检查是否通过验证、会话启动时检查是否有积累的反馈需要处理。

环境强制了元认知循环，而不是靠 Agent 的注意力跨度。

**决策三：晋升，不要压缩**

Agent 的自我模型必须跨会话存活。

标准的做法——把整个对话历史丢进下一个会话——是不可扩展的。能幸存下来的应该是经过晋升的知识：

哪些接口和不变量被验证是持久的？哪些假设被推翻了？哪些技术债务是故意延迟的？哪些失败模式反复出现？

这是第四层的内存系统。没有它，每次会话都是一张白纸——一个永远学不会的工具。

---

## 七、结语

Agent-Native 不是一个你可以安装的包。它是一种设计视角的转变。

当前的讨论止步于三个让 Agent 有能力的层面——内容可读、任务可执行、协议兼容。这些回答的是「Agent 怎么操作产品？」

第四层回答的是更难的问题：「Agent 怎么知道自己操作对了——怎么让自己变得更好？」

有能力但没有自知之明，是工具。

有能力且有自知之明，是操作者。

向第四层前进。

---

*2026 年 7 月。前三层让 Agent 能做事。第四层让 Agent 会做事。别停在三层。*
