# 写一份设计文档 vs 跑一条设计链

> Google 开源了 `DESIGN.md` 格式——YAML token、CLI lint、Tailwind 一键导出。很棒。
> 但格式只能帮"已经知道要什么"的人。0→1 的产品需要的不是一份格式，是一条链。

---

Google Labs 开源了一个[有意思的东西](https://github.com/google-labs-code/design.md)：一种让 AI 编码 Agent 读写设计 token 的标准化格式。

```yaml
colors:
  background: "#ffffff"
  ink: "#08060d"
  accent: "#aa3bff"
```

YAML 里的每个具名值——`#ffffff`、`18px`、`4px`——就是一个 **design token**（设计令牌）：设计系统最小粒度的原子取值，有名字、有数值，让 Agent 做 UI 时不瞎猜。

加一把 CLI：`designmd lint`、`designmd export --format css-tailwind`、`designmd diff`。

看上去很完整。Agent 能读 token 写 UI，设计变更可 diff，还能导出主题文件。

但如果你真的从一个空白项目开始用 AI 写产品，你会发现一个尴尬的事实：

**DESIGN.md 只能帮你"写什么"，帮不了你"定什么"**。

token 是 `#aa3bff` 还是 `#2563eb`，这个决策发生在 DESIGN.md 写入之前。而最痛苦的部分，恰恰是"之前"。

---

## 一、格式是终点，不是路径

Google 的 PHILOSOPHY.md 里有一条我很赞同的：**"prose 决定气质，token 是 prose 的上下文"**。不要写空泛的形容词，要写具体的参照物——"像 1970 年代的讲义"，而不是"复古风格"。

但 prose 怎么来？参照物怎么选？"像 1970 年代讲义"这个决策，在产品 idea 还模糊的时候，谁能拍板？

DESIGN.md 假设你**已经有设计意图**了。它不负责帮你发现意图。

这就是那个 gap：

```
                    ┌─────────────────────────┐
                    │  你有意图 → 写 DESIGN.md │  ← 格式覆盖
                    └─────────────────────────┘
                           ↑
                    ┌─────────────────────────┐
                    │  没有意图 → 怎么走到这？   │  ← 没覆盖
                    └─────────────────────────┘
```

对于已经有设计师、有设计系统、有成熟产品的团队，前半个问题不存在。对于 0→1 阶段的小团队或独立开发者——它才是真正的问题。

---

## 二、链的回答：四条环

格式只覆盖后半段。要覆盖前半段，你需要一条**链**——从模糊想法到具体取值，分环节递进，每环节解决一个特定问题。

### 第 1 环：方向文档——不写具体数值

第一份产出是方向文档：产品的视觉调性是什么、参照什么产品、避免什么风格。

这个阶段**故意不写任何颜色数值**。这不是疏忽，是纪律。如果你在第一轮就写 `#aa3bff`，那个 hex 大概率来自你的"直觉偏好"，而不是来自任何参照物分析。它经不起追问："为什么是这个紫不是那个紫？"

方向文档只产出：调性、参照产品、视觉情绪、反套路检查。全是描述，没有具体数值。

（我在 ReqForge 框架里把这步实现为 Design-Brief 技能——用问卷 + 参照产品分析帮用户澄清意图，产出只有 prose，不含 hex。）

### 第 2 环：原型——像素级验证

用设计工具出可审的视觉稿。这一步的价值不是"好看"，而是**让"抽象描述"变成"具体可否定"的东西**：

- "这里间距太大" → 可以在原型上指出来
- "这颜色不对" → 可以改
- "这个字体看起来太挤" → 能真实看到

人脑在抽象描述（"简洁现代的配色"）和具体像素（"这个灰太冷了"）之间的判断力，差距比你想象的大十倍。

### 第 3 环：原型验收后——强制冻结取值

只有原型被人工验收通过，才进入取值冻结阶段。

冻结的意思是：这个颜色值已经经过至少三轮验证（方向 → 像素 → 人工确认），不再是某个人拍脑袋的产物。

冻结后的规范文件成为**唯一权威来源**。实现者写 UI、审查者审 UI 都优先读这个文件里的数值。设计工具里的稿子可以继续改，但取值只认这份文件。

### 第 4 环：验证期——可检查、可对比、可导出

这是标准格式的强项登场的地方。冻结后的规范文件可以自动化处理：

```bash
npx -p @google/design.md designmd lint DESIGN.md     # 规范性检查
npx -p @google/design.md designmd diff DESIGN.md v2  # 变更追踪
npx -p @google/design.md designmd export --format css-tailwind  # 导出主题
```

但在链的视角里，这一步是**可选的出口**，不是入口。lint 不通过的时候，正确的反应不是"格式有问题就不发布了"，而是先确认取值是否经过了前面三轮验证——因为很多项目根本没有 UI，不需要这层。

## 三、格式和链是互补的

格式和链不是竞争关系。它们解决不同的问题，彼此需要。

| 维度 | 格式（DESIGN.md） | 链（四环流程） |
|------|-------------------|----------------|
| 核心问题 | 怎么写取值 | 怎么定取值 |
| 假设 | 你已有设计意图 | 帮你发现意图 |
| 可验证 | CI 里 lint/diff | 原型验收、追问 |
| 变更追踪 | `designmd diff` | 环间决策记录 |
| 使用场景 | 成熟产品、有设计师 | 0→1、独立开发者 |

Google DESIGN.md 的哲学里有句话：**"specific reference > adjectives"**。你要写"像 1970 年代的讲义"，不要写"复古风格"。

链的逻辑一模一样——它只是把这句话向前推了一步：如果你还没有那个"具体的参照物"，先去找到它，而不是直接写 token。

两条路径都发现了同一个真理：**具体比抽象可信**。格式要求你把 token 写具体，链要求你把 token 的来源也写具体。

## 四、什么时候只需要格式？

公平地说，不是每个项目都需要跑完整条链。

### ✅ 只用格式就够了

- 你有设计师或者已有设计系统
- 你在改版一个现有产品，方向已知
- 你的团队能靠纯描述对齐意图
- 你用其他工具出设计稿，只需要一份规范文件做下游消费

### ❌ 建议跑完整链

- 0→1 新产品，没有参照物
- 你一个人既是 PM 又是开发，设计直觉没验证过
- 项目涉及多人协作，大家说的"简洁"不是同一个"简洁"
- 前一次发货被"设计返工"拖慢过

这个选择不是质量门槛——是**风险门槛**。跳过方向探索直接写取值，赌的是你的直觉足够准。对某些团队和某些产品，这个赌值得打。对多数 0→1 场景，不值得。

---

## 五、写在最后

Google DESIGN.md 是一个优秀的格式提案。它解决了一个真实问题：Agent 没有稳定的取值来源就会瞎猜颜色，猜的颜色多了就会把 UI 写成彩虹。

但格式是终点，不是路径。

真正让取值可信的，不是 YAML 结构定义得好，不是 CLI lint 通过，而是**那个颜色值被追着问了三轮"你确定吗"**——在方向文档里问一次，在原型前问一次，在原型验收时再问一次。

如果答案三遍都一样，那这个颜色大概率是对的。

如果第一遍就直接写进了规范文件，你永远不会知道它在第三遍会不会被推翻。

---

*写于 2026-06。格式让你写得对，链让你写得之前就想得对。两样都需要，但顺序不能反。*
