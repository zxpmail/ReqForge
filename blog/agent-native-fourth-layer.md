# 前三层让 Agent 能做事，第四层让 Agent 会做事

> "Agent-Native" 是今年的 buzzword。大部分解释把它窄化成了"把 AI 绑到前端上"。
> 这不完全错——但它只看到了前三层，漏掉了最关键的一层。

---

## 一、大家都在说的三层

BuilderIO 开源了 agent-native 框架，阿里云在峰会上展示了五款 Agent-Native 产品，技术社区开始大讨论"Agent-Native 设计范式"。一个被反复提及的三层模型逐渐浮现：

**第一层 — 内容可读。** Agent 能把你的内容理解为结构化文本，而不是 JavaScript 渲染的噪音。`llms.txt`、`AGENTS.md` 这类标准解决的是这个问题。

> 测试：一个模型打开你的文档，能不能在不滚动无关内容的情况下找到它需要的接口？

**第二层 — 任务可执行。** Agent 不只是读——它能调用你的 API、触发操作、获取实时数据。`defineAction` 及其等价物解决的是这个问题。

> 测试：Agent 能不能在你的产品里做到人类用户通过 UI 能做的一切——而且完全不碰 UI？

**第三层 — 协议兼容。** Agent 通过标准协议（MCP、A2A）与系统交互，你不用为每个 Agent 写定制适配。一套协议，所有 Agent 都能用。

> 测试：你的系统能不能兼容任何 MCP 兼容的 Agent——还是只能配你自己写的那一个？

这三层回答了同一个问题：**"Agent 怎么操作这个产品？"**

这个问题很对。但它不是唯一的问题。把 Agent-Native 仅仅定义在这三层上，就错过了更难的那一半。

不止如此——社区在传播中还把"原生"窄化成了"原生绑定到前端框架"——具体来说就是 React。让我们来看看为什么这是不对的。

---

## 二、"原生"是原生于运行环境，不是原生于 React

看到 BuilderIO 的的技术栈（React + Nitro + Drizzle），很多人得出结论："Agent-Native 是一种前端架构。" 不是。

一个真正的 Agent-Native 系统，应该让 Agent 通过**稳定的协议**来交互——CLI、HTTP API、MCP、A2A——而不是硬编码到一棵 DOM 树上。UI 只是众多入口之一，而且坦白说，它是最不稳定的那个。

| 层面 | 生命周期 | 风险 |
|------|----------|------|
| UI 框架（React、Vue 等） | 2-5 年 | 换一个框架就得重来 |
| CLI 命令与参数约定 | 20-50 年 | 缓慢演进，向后兼容 |
| 协议（HTTP、SQL、MCP） | 30-50 年 | 从不替换，只会扩展 |

**UI 是易变的**——今天 React，明天 Vue，后天直接语音交互。把 Agent 的逻辑绑死在 DOM 上，前端一重构，Agent 直接失明。

**协议是持久的**——CLI 接口的约定几十年没变过。SQL 语法四十年来没有重新设计过。Agent 应该 Native 在这些稳定的基石上，而不是易变的表现层。

三层模型在精神上是正确的。但它的实现必须是协议优先的，而不是 UI 优先的。

---

## 三、这三层的成就与局限

前三层给你一个**有操作能力**的 Agent——它能读、能做、能互操作。很多团队做到这里就觉得满了。说得过去，大部分产品连第一层都没做完。

但第三层上面有一个无人讨论的空隙。

---

## 四、第四层：元认知

前三层让 Agent *有能力*。但能力没有自知之明是危险的。

第四层回答的是另一个问题——不是"Agent 怎么操作产品？"，而是 **"Agent 怎么知道自己操作对了——做错了又怎么办？"**

这就是元认知层。

### 能力意识

Agent 知道什么事自己能做、什么事自己做不准：

- "这段代码我可以生成，但安全模型应该让人来审。"
- "这个错误模式我之前犯过——先查一下参考文档再动手。"
- "这个问题不在我的能力范围内——转给专家系统。"

没有这个，一个拥有前三层的 Agent 会自信地尝试所有它能触及的事。一个强大的工具，却没有边界感。

### 自我进化

Agent 注意到自己的失败模式，并自我修正：

- "同样的 PostgreSQL 迁移错误我已经犯了三次了。我应该写一份参考文档，以后生成迁移之前先查一下。"
- "这个错误模式在反馈里反复出现——我应该提出一个新的规则来预防。"
- "反馈条目积累了 12 条——是时候触发一次进化周期，审视自己的启发式规则了。"

这是"等着人来修的工具"和"维护自己能力的操作者"之间的区别。

### 优雅降级

Agent 能说清楚自己*为什么*做不了：

- "我不能改这个文件——它不在当前阶段的范围内。"
- "我不能回答这个问题——它不是我当前配置的领域。"
- "我发现了规格和代码之间的矛盾。我会把它标记出来，而不是默默选一个。"

用产品语言说：前三层让 Agent 成为你产品的**高级用户**。第四层把它变成了一个**负责任的运营者**——在问题出现时会主动"拉闸"。

```
Agent-Native 成熟度模型

第四层：元认知        ← Agent 认识自己
  │   能力意识 · 自我进化 · 优雅降级
  │
第三层：协议兼容      ← Agent 可以互操作
  │   MCP、A2A 等标准协议
  │
第二层：任务可执行    ← Agent 可以动手
  │   defineAction、共享操作
  │
第一层：内容可读      ← Agent 可以阅读
       llms.txt、结构化文档、干净内容
```

## 五、两种架构，同一个哲学

两个挂着"Agent-Native"标签的框架，采用了截然不同的架构。这个对比的价值在于它说明**第四层是一个设计选择**，不是技术上的偶然。

| | BuilderIO agent-native | ReqForge |
|---|---|---|
| 面向领域 | SaaS 产品 | 工程工具 |
| 主要界面 | React UI + Agent | CLI + 文件系统 |
| 共享状态 | 数据库（Drizzle） | 文件系统（git） |
| 操作方式 | defineAction | Skill 命令 + Hook |
| 元认知路线 | 审计日志 + 权限控制 | 反馈循环 + 自我改进 |

两者共享同一核心哲学——Agent 是原生操作者，不是聊天插件。但它们在第四层上的选择截然不同。

BuilderIO 把元认知当成**审计问题**——记录谁干了什么，用 RBAC 划边界。这对 SaaS 产品来说是合理的：人类是主要操作者，Agent 是受控的助手。

ReqForge 把元认知当成**操作系统问题**——在执行路径上插入钩子，强制正确性、积累反馈、触发自我改进。在工程工具领域，Agent 是自主的操作者，自我修正能力比权限划分更重要。

两种路线都是对的。差异不是"谁更好"——而是**领域塑造**的。关键在于第四层*存在*，不论以什么形态。

## 六、走向第四层的三个具体决策

如果你今天在设计一个 Agent-Native 系统，希望朝第四层迈进，有三个现在就可以做的决策。

### 1. 让状态透明

当 Agent 和人类共享一个状态层时，Agent 的历史也是它的自我模型。如果共享状态是数据库，你需要不可篡改的审计日志和 OT/CRDT 来追踪谁做了什么——而且 Agent 需要能在行动前查询这些日志。如果共享状态是**文件系统**（或者任何天生带版本管理的存储），`git log` *就是*审计线索——Agent 读自己的历史，从自己的错误中学习。

在 SaaS 场景中，透明意味着让每一个 Agent 的行为通过 Agent 自己使用的接口也能被观察到——而不是藏在某个独立管理后台里。最紧凑的反馈循环是："Agent 在决定下一步之前，能看到自己上一步的后果。"

透明才能自我修正。看不到自己做了什么的人，改不了。

### 2. 在环境层面强制约束，不是在提示词层面

把元认知检查写在系统提示词里是脆弱的。换一个模型版本、换一种提示词结构，Agent 就"忘记"自我检查了。

稳健的做法是**钩子（hook）**——在特定的执行点运行的拦截器，不管模型怎么决定都会触发：

- 写代码之前：规格确认了吗？
- 生成之后：这个引用真的存在吗？
- 声称"完成"时：通过验证了吗？
- 会话启动时：有积累的反馈需要处理吗？

环境强制了元认知循环，而不是靠 Agent 的注意力跨度。

在数据库驱动的 SaaS 里，等价物是请求中间件——不是在系统提示词里写一句"你应该先检查权限再写入"，而是中间件在到达数据库之前就直接拒绝未授权的写入。原理是一样的：**把把关从"让 Agent 记住"移到"环境不允许"**。

### 3. 晋升，不要压缩

Agent 的自我模型必须跨会话存活。标准的做法——把整个对话历史丢进下一个会话——不可扩展。能幸存下来的应该是 **晋升（promoted）** 的知识：

- 哪些接口和不变量被验证是持久的？
- 哪些假设被推翻了？
- 哪些技术债务是故意延迟的？
- 哪些失败模式反复出现？

这是第四层的内存系统。没有它，每次会话都是一张白纸——一个永远学不会的工具。

---

## 七、结语

Agent-Native 不是一个你可以安装的包。它是一种设计视角的转变。当前的讨论止步于三个让 Agent *有能力*的层面——内容可读、任务可执行、协议兼容。这些回答的是"Agent 怎么操作产品？"

第四层回答的是更难的问题：**"Agent 怎么知道自己操作对了——怎么让自己变得更好？"**

有能力但没有自知之明，是工具。有能力且有自知之明，是操作者。

下一次当你听到有人说"我们的产品是 Agent-Native 的"，不妨问一个简单的问题：

> "你的 Agent 知道自己刚才做对了没有？"

如果答案不是"能"，那它可能只走完了前三层。

向第四层前进。

---

*2026 年 7 月。前三层让 Agent 能做事。第四层让 Agent 会做事。别停在三层。*
