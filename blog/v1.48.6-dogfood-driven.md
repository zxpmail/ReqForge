# v1.48.6：七个改动，七次被自己的框架咬过的经历

> 每个改动都对应一次真实的狗粮（dogfood）场景。没有理论，只有教训。

---

## 1. DESIGN.md 冻结 — 因为设计稿无处可寻

**来源**：dogfood #2（读书追踪 Web 应用）

做完 mockup 后，花了一个 Phase 的时间，在 "这个按钮是什么颜色" 和 "间距是多少 px" 这类问题上反复来回。Design-Brief 只记录了方向（"暖色调、轻盈"），没有精确值。设计工具里的 token 倒是精确，但开发工具 MCP 不一定每次都连得上。

结果：每次读设计稿都像考古——翻截图、猜色值、试间距。

**修复**：design-maker 在做完 mockup 后冻结一份 `DESIGN.md`，把设计 token 写死进文件系统。用 Google 的 [design.md](https://github.com/google-labs-code/design.md) 格式——YAML token + Markdown rationale，可直接 lint、导出 Tailwind CSS 变量。dev-builder 读样式的优先级变成 `DESIGN.md` > 设计工具 MCP > Design-Brief。

**狗粮教训**：设计链没有"冻结点"，每次实现都是模糊匹配。

## 2. 幽灵门修正 — 因为检查了自己写的合约

**来源**：一次框架自身审计

ReqForge 的 CLAUDE.md 声称有 4 道机器门（Machine Gates）：Spec-Before-Code、Hallucination、Sloppiness、Overstepping。检查实际 hooks 目录时发现——**Sloppiness Gate 和 Overstepping Gate 没有对应 hook 文件。**

Sloppiness 实际上的 enforcement 在 `forge-verify` → `phase-exit-guard`（stop-time 拦未验证的完成声明），不是 CLAUDE.md 说的 PreToolUse 写链。Overstepping 则根本没有 enforcement——它的真实实现是 Phase-boundary-detector，当时还是 deferred 状态。

**修复**：修正 CLAUDE.md/AGENTS.md 的合约文本，让每次声明都对得上实际 enforcement。升级 machine-gates-doc 冒烟测试从"检查名字存在"变成"检查 enforcement 文件存在"——25 道检查，幽灵门过不了 CI。

**狗粮教训**：框架自己的合约也会漂移。写 enforcement 的人和不读 hook 的人不是同一个。

---

## 3. Nature Gate 尺寸预检查 — 因为小阶段不配隔离开销

**来源**：dogfood #3（`@forge/ecosystem-cache` CLI 工具）

一个 5 Phase 的 CLI 项目，按规则全部是 Backend Nature → 必须 dispatch implementer。但实际跑下来，Phase 2-4 每个只有 1-2 个文件、3-5 个交付物。implementer 冷启动 2-5 秒 + 打包隔离包的开销，比实际写代码还长。

之前只有 UI/Integration 能跳过 implementer。dogfood #3 证明 Backend/Data 里也有不值得隔离的小阶段。

**修复**：Nature Gate 增加 Size pre-check。≤3 个 Key Files **且** ≤5 个 Deliverables → Small Phase，跳过 implementer。文档、SKILL.md HARD-GATE、sub-agent-isolation 决策表全部同步更新。

**狗粮教训**：阶段 Nature 告诉你能不能隔离，阶段大小告诉你值不值得隔离。两个维度缺一不可。

---

## 4. Phase 边界检测器 — 因为 implementer 做了下一阶段的活

**来源**：dogfood #2 implementer 批量交付

Phase 1 implementer 在一次调用中交付了 Phase 1-3 的所有代码（database schema + CRUD + 搜索 + 分页 + UI 骨架）。功能是好的，但违背了 Phase 拆分意图——Phase 2-3 变成了零实施开销的"幽灵阶段"。

**修复**：implementer 的 `files_to_modify` 从建议性变成约束性——只创建/修改这个列表里的文件。越界写标记为 `DONE_WITH_CONCERNS`。implementer 返还后，dev-builder Step 8.5 做交叉核对：`file_changes` vs `files_to_modify`。越界文件升级给用户三选一（合并/拒绝/重新计划）。这就是 Overstepping Gate 的第一个真实 enforcement。

**狗粮教训**：如果不检查边界，阶段拆分就只是注释。

---

## 5. 设计工具卡顿修复 — 因为设计师卡了 15 分钟

**来源**：dogfood #2 design-maker 卡死

一次性生成 P1-P4 四个页面的 mockup，AI 卡在长思考链里 15-20 分钟不落盘。零输出。你只能 Esc 中断，手动分批。

**根因**：design-maker 的 workflow 说"一页一页设计"，但没有强制每页产出的检查点。AI 倾向于"想清楚再写"——结果一直在想。

**修复**：每步加检查点。设置设计 token 后写 `00-tokens-done.md`，创建组件后写 `01-components-done.md`，每页完成后写 `page-checkpoint.md`。HARD-GATE 标记"不得跳过"。检查点还充当崩溃恢复索引——如果会话中断，下一个 session 知道从哪继续。

**狗粮教训**：工作流说"这样做"不等于 AI 会这样做。如果不强制产出中间产物，它就会一直"想"。

## 6. 尺寸感知路由 — 因为小产品也被过度澄清

**来源**：dogfood #2 的用户体验反馈

跑 product-spec-builder 后被连问"项目目录？有没有 UI？"——而 Product-Spec.md 已经存在、流程明确，本可以直接走 `/dev-planner`。

根因：startup-check 的默认路径是 `Otherwise → 0-to-1`（深度全流程）。小产品也被全量访谈。虽然有 4 种 mode（Quick / Light Grill / Distillation / 0-to-1）让用户手动选轻路径，但默认的 catch-all 是重的。

**修复**：startup-check 的 "Otherwise → 0-to-1" 替换为尺寸感知路由——读取用户请求判断大小：小产品（CLI / ≤4 功能 / 无认证 / 无数据库）→ 默认 Quick；中/大 → 默认 0-to-1。用户仍然可以关键词触达指定 mode。0-to-1 从默认变成按需 opt-in。

**狗粮教训**：给用户选择不等于解决痛点——默认路径才是真的路径。

---

## 7. 包完整性冒烟测试 — 因为发布路径从未被测试

**来源**：dogfood #3 的"发布"阶段

写了 `prepublishOnly` 脚本，配了 CI，跑了 dry-run——然后问了自己：这个路径有没有被任何测试覆盖过？没有。

如果 `package.json` 的 `bin` 路径写了但文件被移动、`files` 白名单忘了包括新目录、或者 `forge-hooks` 引用了不存在的 hook——没有任何测试会发现。

**修复**：forge-smoke 新增 `package-integrity.mjs`，39 道检查验证 package.json 结构、scripts 目标存在、hooks 文件引用有效、bin 入口可寻、files 白名单路径真实。无网络调用（Windows 上 publish dry-run 的 spawnSync 会挂）。forge-smoke 从 13 项 → 14 项。

**狗粮教训**：如果你不测试发布路径，那你不是真的能发布。
