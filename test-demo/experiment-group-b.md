### Items requiring resolution
1. [blocked] API key security model — User's LLM API keys handled in frontend with known browser security risks (exposure via XSS, dev tools). Confirm: (a) do target users accept this? (b) are there CORS issues preventing direct browser API calls? (c) should keys be stored only in localStorage or support session-only input? This determines the entire architecture.
2. [blocked] Data persistence reliability — IndexedDB can silently clear data under certain conditions. For a tool that may contain tens of thousands of characters of creative writing, data loss is unacceptable. Decide: auto-export strategy, explicit data recovery feature, or accept risk and document.
3. [clarify] Non-linear writing support — When a user wants to change character settings while on chapter 12, the current sequential flow doesn't specify whether this updates existing chapters, invalidates them, or does nothing. Decide: (a) allow editing characters anytime with a warning, (b) lock characters after chapter generation, (c) mark as [TBD] and resolve during development.
4. [clarify] Generation quality fallback — If LLM output is poor, what are the user's options? Currently only "manual modification". Decide whether to add: (a) regenerate button with prompt adjustment, (b) paragraph-level regeneration, (c) accept manual outline editing as a more explicit workflow step before generation. Can mark as [TBD] in spec.
5. [clarify] `relationships[]` structure vs free text — Data model includes a structured `relationships[]` array but v1 has no relationship UI. Decide: simplify to free-text relationship field on character card in v1, add structured data when v2 adds visualization.
